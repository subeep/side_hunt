# Azentio hackathon requirements digest (source: /home/sudeep/Downloads/problem_explanation_ceefrj5dzg8.pdf, 12 pages — Read it with the Read tool `pages` param if you need the exact wording of a section)

Goal: azentio.ai = enterprise AI website + secure collaboration portal. Showcases offerings, gives employees and clients distinct exclusive experiences, turns client market observations into GOVERNED collective learning and product improvement. Access MUST be enforced on the server, including direct API and media requests. (The reference prototype has public Admin/Playground/Live — that is a demo convenience, NOT the security model.)

## 01 Experience to deliver
- Public visitor: understands offerings, explores product info + media, requests a demo or registers hackathon interest.
- Employee: signs in, explores internal experiments + broadcasts, contributes to innovation within permissions.
- Client: signs in to an org-specific workspace, accesses entitled demos + content, contributes market observations with an EXPLICIT sharing choice.
- Moderator: reviews proposed shared observations. Approved, de-identified contributions become searchable learning for authorised participants.
- Product owner: connects recurring themes to improvement ideas, communicates status WITHOUT exposing a client's private information.

## 02 Scope
Three different things: (1) Collective learning hub = REQUIRED community workflow (clients submit observations; reviewed contributions + safe summaries shared with authorised participants). (2) Federated ML = separate opt-in P2 track; a discussion board / central doc repo is NOT federated ML. (3) AI-assisted synthesis (AIRA / insight service) = summarises PERMITTED evidence and cites approved contributions; retrieval+summarisation do NOT retrain a model. Out of scope: building the actual credit/reporting/document products — demonstrate approved sandbox workflows with SYNTHETIC data; no prod integrations/billing/client-model deployment.

## 03 Personas & boundaries
| Persona | Permitted | Boundary |
| Public visitor | public catalogue, solutions, approved media, insights, about, demo enquiries, event registration | no private workspaces, client observations, internal broadcasts, config writes |
| Employee | internal dashboard, employee Playground, internal learning, employee broadcasts, assigned collaboration work | verified work identity + approved membership; NO automatic access to every client's private info |
| Client member | own-org workspace, entitled demos+sessions, own/team observations, approved shared learning | tenant + entitlement checks on every protected resource; no employee-only experiments |
| Client administrator | manage invitations + approved roles within OWN org | cannot grant platform roles, change another tenant, or self-enable restricted products |
| Learning moderator | review submitted contributions, redact proposed shared copies, publish/reject/withdraw/investigate reports | no unrestricted access to UNSUBMITTED client-private drafts |
| Content publisher | website banners, public content, permitted video audiences | no identity admin, no implicit access to private learning records |
| Portal administrator | orgs, role grants, config, operational controls | privileged actions audited; private client content requires an explicit support/moderation authorisation, not a broad UI role |
IAM-01: server-side RBAC + tenant membership + resource audience + product entitlement. A user may have multiple memberships; require an explicit ACTIVE workspace when needed. NEVER derive authority from a nav menu, localStorage flag, email suffix alone, or user-supplied tenant ID.
IAM-02: least-privilege defaults. Employee != admin. Permissions to publish videos, moderate learning, invite users, change roles are SEPARATE grants. Deny unless permission + audience conditions satisfied.
REQUIRED ACCESS RULE: an authenticated user may access a resource only when its audience permits their identity, their active tenant/membership is valid where applicable, and the action is authorised. Public resources are EXPLICITLY marked public; public is not a fallback for missing access metadata.

## 04 Login / onboarding
Employees: identity verified for @azentio.com + approved employee membership (prod: Entra OIDC; here: real managed email-code flow + organiser-approved provisioning = employee_allowlist). Clients join by invitation or approval workflow tied to a registered client org; client admin invites only into own org. An account with an arbitrary external email must NOT automatically create a trusted tenant membership.
First-time client journey: single-use expiring invitation (identifies org + proposed role) -> verify identity -> accept only for the intended verified account -> review workspace terms + learning-sharing explanation (JOINING IS NOT CONSENT TO SHARE OR TRAIN) -> land on correct client dashboard with only entitled features; show active org + workspace switcher for multi-membership.

## 05 Employee experience
Dashboard with quick links (Playground, internal Live sessions, experiments, assigned improvement ideas, permitted collective-learning work); separate public product info from internal prototype notes + employee-only sessions. Guided Playground using SYNTHETIC scenarios: choose offering, inspect inputs, run deterministic or AI-assisted demo, review evidence, give structured feedback; label sample data + simulated outputs clearly; never imply a sandbox recommendation is an approved credit/business decision. Internal live broadcasts + recordings restricted to configured employee audience; publishing grant can configure sessions/recordings; ordinary employees cannot change broadcasts or homepage content. Assigned product owner can review approved themes, create improvement idea, link contributions, update status; assignment grants access ONLY to evidence explicitly shared for that purpose. Also: employee experiment submissions, hackathon team spaces, release notes, internal knowledge library with owners, review dates, feedback loops. Employee-only content NEVER enters public/client search or AIRA responses.

## 06 Client experience
Dashboard: active org, entitled offerings, approved product demos, relevant sessions, contribution status, improvement ideas visible to that client; empty states when nothing assigned; never show another tenant's data as sample content. Entitled sandbox demos with synthetic (or explicitly approved client) data; isolate runs, uploaded evidence and saved scenarios by tenant AND user permission; client cannot reach employee-only models/prompts/roadmaps by knowing URLs. "My observations" and, where permitted, "Our organisation's observations": save drafts, submit for review, follow status, amend a RETURNED submission, withdraw a shared contribution. Private org knowledge and the cross-client shared feed must be visually AND technically distinct. Browse/search approved shared observations + safe aggregated themes; filters: offering, industry, region, observation period, topic; search, counts, suggestions and exports must apply the SAME visibility rules as underlying records. Client admins invite/revoke members and grant approved client roles within own org; show membership + invitation states; prevent escalation to employee/moderator/publisher/portal-admin. Relevant improvement ideas with plain-language status, owner/team, last update; public/shared status must not disclose private client tickets, internal prioritisation discussions or unapproved delivery commitments. Also: saved searches, bookmarks, notifications, collaborative comments, contribution acknowledgements, support-ticket integration, client-specific resources — comments + attachments INHERIT the parent resource's audience; moderation + reporting apply to them too. Suggested: entitled sandboxes + guided demos; client briefings, release notes, invitation-only webinars; private contribution tracking + org admin; approved cross-client learning, safe trend digests, improvement-status updates.

## 07 Observation capture
Structured form: market observations, emerging trends, product gaps, operational challenges, successful practices, improvement suggestions. START AS PRIVATE DRAFT. NEVER shared merely because user clicked Save. Validate required fields + lengths on BOTH client and server. Actions: draft, submit, edit-returned, withdraw. Attachments optional in P0 (support links instead; if supported: type/size limits, private storage, same audience controls). Prompt users to exclude customer identities, account numbers, transaction-level data, credentials, confidential contractual terms. A warning or automated scan is not a privacy guarantee. FLAG likely sensitive content for review before any shared publication.

## 08 Review / publication / withdrawal
Explicit allowed lifecycle transitions + audit events. Keep original PRIVATE source separate from the approved shared representation; a published copy contains ONLY reviewed fields, not the source's hidden metadata/attachments. Moderators: redact, request clarification, reject duplicates or unsafe material, publish approved version; notify author in-app of state changes. Material edits to a published contribution create a NEW version + require renewed review; never silently widen an audience. REPORT-contribution action (misleading / confidential / inappropriate); moderator can temporarily unpublish during review, record decision, inform contributor; do NOT require the reporting client to disclose another client's identity. WITHDRAWAL must invalidate search/index/cache entries and future AIRA retrieval — demonstrate synchronously or within 60 s; state production propagation SLA; explain that already-viewed material and third-party copies cannot be recalled automatically. Notification discipline: persisted notification/outbox records + idempotent delivery when email added. In-app status = P0; provider-backed email = P1. A successful submission / stored notification / queued email must NOT be labelled "email delivered".

## 09 Sharing, consent, confidentiality
Sharing choices: private to author | within my organisation | proposed sharing with approved learning community. Org-only content NEVER becomes shared by default; broadening visibility requires explicit author permission + moderation. Record SEPARATE permissions for (a) storing/processing, (b) publishing its reviewed shared representation, (c) disclosing author/org attribution, (d) any future training/federated programme. Membership, publishing consent and model-training consent are NOT interchangeable.
Cross-client publication: keep tenant IDs, private author profiles, original attachments, internal reviewer notes OUT of shared response payloads. De-identified wording by default; org attribution is opt-in AND must pass review; removing a name alone doesn't make a rare observation anonymous. Reduce over-specific geography/dates/unusual transaction details. No confidential pricing, customer-level financial records, secrets. Keep raw private records out of shared analytics, vector indexes, logs and AI provider payloads unless policy explicitly permits. Show the contributor who can see each version and how it may be used; withdrawal accessible; retain consent history, approved version and moderation decisions per a documented policy; do NOT claim withdrawal can undo an already-trained model.
Aggregation safeguards: configurable MIN distinct contributing organisations for shared trend statistics (judging: >= 3 synthetic client orgs; prod threshold + suppression policy + stronger controls need approval pre-launch). Suppress small cohorts, sensitive breakdowns and differencing-friendly filters; a min cohort size alone is not a privacy guarantee.

## 10 Insights -> better offerings
Searchable approved feed + basic theme dashboard: theme, relevant offerings, supporting approved contributions, observation period, number of DISTINCT contributing orgs where safe, confidence/limitations, latest update. NEVER count repeated posts from one org as independent cross-client evidence. Product owners create improvement ideas linked to PERMITTED evidence. Fields: title, problem statement, offering, supporting contribution refs, proposed outcome, owner/team, priority, status, last update. Statuses: Proposed, Under review, Planned, In progress, Released, Not proceeding; status changes audited. Close the loop with contributors via audience-appropriate status updates: may describe a theme + improvement decision; must NOT expose private source material, confidential internal roadmaps or another client's support case.
Illustrative scenario (build this as seed data): three fictional client orgs submit observations about inconsistent treatment of seasonal SME cash flow (each with observation period, evidence type, confidence label) -> moderator removes identifying details, requests one clarification, publishes approved shared versions -> dashboard groups into a "Seasonality context" theme with links to permitted evidence + small-sample warning -> product owner creates idea for "Financial Analysis Intelligence: add a seasonality-aware comparison explanation", status Under review, NOT a promised delivery -> clients see shared theme + status; private drafts + moderation notes stay private; no product model changes automatically.
Also: semantic clustering, duplicate detection, trend-change summaries, subscription digests, assisted prioritisation. Generated themes MUST preserve evidence links + uncertainty; popularity alone must not be presented as market prevalence or proof of causation. Quality feedback (useful / needs evidence), transparent moderation reasons, reviewer-assessed evidence quality. NO leaderboards that pressure disclosure or reward volume over quality.

## 11 Optional federated model-learning track (P2)
Genuine FL only as a separate opt-in programme; >=3 isolated synthetic client datasets; local training, aggregation round, global eval on separate synthetic holdout; report participation, weighting, metrics vs simple baseline; log consent, participants, model/update versions, aggregation method, eval outcomes (no training examples in coordinator logs); validate client updates, dropout scenario, explain skew effects; aggregate = candidate model needing human review + explicit deployment decision + rollback design. Document threat model (update leakage, poisoning). Describe/implement clipping, poisoning checks, DP with declared accounting if used; label simulated controls honestly; plain averaging must not claim secure aggregation/formal privacy. Withdrawal + lineage policy; never promise automatic "untraining".
