# azentio.ai Website & Intelligent Collaboration Portal

Hackathon build. Read `docs/REQUIREMENTS.md` (digest of the brief) before coding; `docs/PROTOTYPE_CONTENT.md` has copy for the public site.

## Stack
Next.js 16 (App Router, Turbopack, React 19, TS strict), Tailwind v4 (theme tokens in `src/app/globals.css`), Drizzle ORM. DB: Postgres via `pg` when `DATABASE_URL` set (Neon on Vercel), otherwise embedded PGlite in `.data/` (auto schema + seed). Auth: own email-code flow + DB sessions (httpOnly cookie). Deploys to Vercel. Theme: **off-white + brown** only (use `bg-paper`, `bg-card`, `text-ink`, `text-muted`, `brown-*`, `sage`, `clay`, `amber` tokens and the `.card .btn .badge .input .alert .table-basic` classes). No bright blue/purple/green.

## Non-negotiable security rules (the brief is judged on these)
1. **Every** page, server action and route handler that touches protected data must authorise on the server via `src/lib/authz` (`authorize`, `canSeeAudience`, `audienceFilter`, `canReadTenantPrivate`) and/or guards in `src/lib/authz/guards.ts` (`requireUser/Employee/Grant/Client/ClientAdmin/Action`). Default deny. Never trust the nav, a hidden field, a cookie flag, an email suffix, or a client-supplied tenant/org id.
2. Tenant = `principal.activeOrgId` (server validated). A client-supplied `orgId` may only be used as a lookup key that is then checked to EQUAL the principal's active org, or checked via membership; never as authority.
3. Resources carry audience metadata (`audience_kind/audience_org_id/audience_product`). NULL kind = deny. Lists, counts, search, suggestions, exports and media must use the same rule (`audienceFilter` SQL twin). Unauthorised direct access to an object id returns 404 (or 403 for role guards) and writes an audit `deny` event where sensible. Never leak existence/counts.
4. Protected media is stored in DB and served ONLY through an authorising route handler. Nothing sensitive in `/public`.
5. Mutating route handlers must check `sameOrigin(req)` (`src/lib/http.ts`) and the principal. Server actions: call a guard first. Validate all input with zod on the server (lengths, enums).
6. Never serialise `shared_contributions.org_id`, `contribution_id`, `published_by`, author ids/emails, reviewer notes, tenant ids into anything a client/other tenant receives. Select shared rows with `sharedPublicColumns` from `src/lib/learning/columns.ts`.
7. Privileged and security-relevant actions write `audit(...)` (`src/lib/audit.ts`). Notifications via `notify(...)` (idempotent dedupeKey). Never label queued/stored email as "delivered".
8. Synthetic data only. Label sample/simulated outputs clearly. Do not imply sandbox output is an approved credit/business decision.
9. Do not write fake security: no `localStorage` role flags, no "demo bypass" routes besides the existing `/demo` persona sign-in (DEMO_MODE=1 only).

## Engineering conventions
- Server components by default; `'use client'` only for interactive widgets. Forms post to server actions (`'use server'`, in `actions.ts` next to the page) using `useActionState` + `SubmitButton` where feedback is needed. Next 16: `params`/`searchParams`/`cookies()`/`headers()` are async.
- Every page must render a sensible EMPTY state and an error state. Accessible: labels, aria, focus states, keyboard usable, responsive (mobile-first).
- Keep files small and cohesive. Match the existing code style (see `src/lib/auth/*`, `src/components/ui`). No new dependencies unless essential (state it in your report). Do NOT add dependencies for icons/UI kits.
- **Do NOT run `next dev`, `next start` or `next build`** (shared `.next/` dir and shared DB dir would clash with parallel agents). Verify with `npx tsc --noEmit` (errors in other areas' files that are mid-edit are not yours: filter by your paths) and `npx vitest run tests/<yourarea>` (tests use in-memory PGlite; see `tests/foundation.test.ts` + `tests/helpers/principals.ts` for how to build a principal for any seed persona with `as(USER.x, activeOrgId?)`). Test server logic by calling lib functions directly; for pages/handlers keep logic in lib functions so it is testable.
- Tests are the acceptance tests of the brief for your area: write meaningful negative tests (cross-tenant, wrong role, direct id access, missing audience metadata, escalation attempts) — not only happy paths.
- When finished, report: files created, routes, anything you could not finish, any core-file edits, and any contract assumptions about other areas.
